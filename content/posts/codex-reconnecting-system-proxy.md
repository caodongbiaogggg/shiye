使用 Codex 时，最影响节奏的一种情况是：问题已经发出，回复还没开始，界面却在反复提示重新连接。

```text
Reconnecting 1/5
Reconnecting 2/5
Reconnecting 3/5
Reconnecting 4/5
Reconnecting 5/5
```

几轮等待下来，几十秒甚至几分钟就过去了。原本只是想问一个简单的问题，却被连接状态打断了思路。

![Codex 对话界面显示“正在重新连接 4/5”](./images/codex-reconnecting.png)

*图 1：提问后出现的重连提示。截图记录的是连接状态，不是完整的网络诊断结果。*

这篇笔记围绕下面这行配置展开：

```toml
respect_system_proxy = true
```

**先说明适用边界：这不是已经得到官方文档确认的通用修复方案。** 截至 2026 年 9 月 9 日，查阅的 [OpenAI 官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)未列出这一配置项。因此，不能仅凭“文件里添加成功”，判断当前版本已经识别并启用了它。下面保留配置尝试的步骤，也说明如何判断它是否真正有帮助。

## 一、先区分：是在思考，还是在重连？

看到 `Reconnecting`，应当先关注连接是否稳定，而不是直接认为模型在进行长时间思考。

但这条提示本身，不能证明具体是哪一段网络出了问题。尤其不能据此断言：

- 只有使用代理时才会出现重连；
- 客户端一定先直连、完全不使用系统代理；
- 重试五次后一定会自动切换到代理。

这些判断需要对应版本的实现说明或日志支持。这里更合适的排查方向是：**当前客户端的连接方式，是否与电脑正在使用的网络配置一致？**

## 二、修改前，先确认两件事

第一，确认代理本身已经正常启用，并记下当前使用的客户端和版本。不同客户端、不同版本的配置支持情况可能不同，不能直接照搬。

第二，备份原来的 `config.toml`。这次只调整一个配置项，方便比较结果，也方便在无效或报错时恢复。

如果无法确认当前版本支持 `respect_system_proxy`，把它当作待验证的尝试，不要把它当作必需设置。

## 三、macOS 上的配置操作

### 1. 找到配置文件

在 macOS 打开 Finder（访达），按下：

```text
Shift + Command + G
```

输入文件夹路径：

```text
~/.codex/
```

进入后，找到 `config.toml`，先复制一份备份，再用纯文本编辑器打开。

`~` 代表当前用户的主目录。默认的用户级配置路径可参考 [OpenAI 配置基础文档](https://learn.chatgpt.com/docs/config-file/config-basic)；如果你自行调整过配置目录，应以实际使用的位置为准。

### 2. 在已有的 features 区域加入配置

找到文件中的 `[features]`，在该区域添加：

```toml
[features]
respect_system_proxy = true
```

**如果已经存在 `[features]`，只加下面那一行，不要再创建一个同名区域。** 如果已经存在 `respect_system_proxy`，修改原有值即可，也不要重复添加。

这里的“该区域”指 `[features]` 到下一个 `[其他区域]` 之前。不要把配置随意加到文件末尾，以免落入其他区域。

![config.toml 中 features 区域的系统代理配置示例](./images/codex-system-proxy-config.png)

*图 2：配置项的位置示例。截图中的其他设置与这次操作无关，无需照抄；截图也不代表当前版本一定支持该项。*

### 3. 保存并重启实际使用的客户端

保持文件名为 `config.toml`，不要保存成 `config.toml.txt` 或富文本格式。

保存后，完全退出并重新打开实际使用的 Codex 客户端。如果是在 ChatGPT 中使用相关功能，则重启对应应用，再进行相同条件下的测试。

## 四、如何判断有没有改善？

修改配置后，可以先发送一个简单问题，例如“你好”，观察从发出请求到出现首段回复的过程。尽量保持网络和测试问题一致，多试几次，避免把一次偶然成功当成修复完成。

| 观察项 | 修改前记录什么 | 修改后检查什么 |
| --- | --- | --- |
| 重连提示 | 是否出现，最高到几次 | 是否减少或仍反复出现 |
| 首次响应等待 | 从发送到首段回复大约多久 | 相同条件下是否缩短 |
| 配置提示 | 是否已有错误或警告 | 是否出现未知配置、解析失败等提示 |
| 稳定性 | 多次请求的表现 | 改善能否重复出现 |

如果重连减少、等待缩短，可以记录为“在当前版本和网络环境下，调整后体验有所改善”。

但 **进入 `Thinking` 不等于马上完成回答，重连消失也不等于所有请求都能秒回**。连接建立和模型生成是不同阶段，不宜用一次测试为后续速度作保证。

## 五、如果修改后仍然无效

不要继续重复堆叠配置。先检查：

1. **文件是否正确**：是否编辑了客户端实际读取的配置文件？
2. **格式是否正确**：是否重复创建了 `[features]`，或把配置写进了其他区域？
3. **版本是否支持**：是否出现未知配置项或相关警告？没有警告也不能单独证明已生效。
4. **网络是否稳定**：代理本身是否可用，连接是否仍然中断？

如果新增设置后出现异常，先移除这次添加的行，或恢复备份，再重新启动客户端。后续排查时，保留客户端版本、重连时间和相关错误信息，比只描述“很卡”更容易定位问题。

## 写在最后

这次记录的重点，不只是往配置文件里加一行文字，而是把“等待回复”拆开看：到底是在等待连接，还是在等待生成？

遇到反复重连时，检查代理与客户端连接配置是一个排查方向；至于 `respect_system_proxy = true` 是否适用，应结合具体版本确认，并通过实际测试判断。

**记录现象，单独改动，比较结果。比起“一行代码包治重连”，这样的记录更方便下次复用。**
